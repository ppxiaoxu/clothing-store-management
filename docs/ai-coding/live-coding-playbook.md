# 30—45 分钟现场 AI Coding 实战指南

现场的目标是交付一个能解释、能验证、能演示的小功能。人负责需求取舍、关键判断和验收，AI 负责带着明确上下文读代码、生成局部改动和辅助排障。

先读 [仓库约定](../../AGENTS.md) 和 [业务词表](../../GLOSSARY.md)。下文用“SKU 列表增加临时低库存阈值筛选”贯穿演示；接口、测试和提示词是现场实施的设计，实际进度以现场输出为准。

## 先用五个问题确定现场条件

将环境问题合并问清，业务问题给出默认建议，总共控制在 3—5 个关键问题；有明确答案的内容不重复询问。

1. **工具与网络**：可以用哪种 AI、终端和浏览器？能否联网、安装依赖或读取本地 Skills？建议优先使用现成工具。
2. **现有环境**：后端、前端、测试数据库和测试账号是否可用？是否有可运行基线和隔离数据？先跑一个最短基线检查，避免把环境故障当成新功能缺陷。
3. **交付标准**：可用时间是 30 还是 45 分钟？期待接口、页面、测试还是全部？建议交付一个完整用户行为，并保留最后五分钟演示；是否允许本地提交另行确认。
4. **业务口径**：低库存是否定义为 `stock <= 阈值`？建议包含相等值和零库存；阈值只是本次列表查询条件，不保存为全店配置，并与颜色、尺码取交集。
5. **范围与异常**：建议保留原查询，不传阈值即不筛库存；负数和非整数返回参数错误，搜索与重置回到第一页。是否认可这个最小范围和 API 验证接口？

对面试官可以这样说：

> 我先把工具限制、可运行环境和验收标准对齐，再确认两处业务边界。这样能把时间花在一个完整功能上，也能让您看到每一步为什么做、怎么判断完成。

若答案与本文不同，立即改微规格和测试期望，后面的提示词一起调整。

## 时间怎么分

| 环节 | 30 分钟安排 | 45 分钟安排 | 必须留下的结果 |
| --- | --- | --- | --- |
| 确认规则、验证基线 | 0—3 分钟 | 0—4 分钟 | 工具、环境、验收范围；记录开始时的提交与已有改动 |
| 定位代码、确认口径 | 3—7 分钟 | 4—10 分钟 | 已有能力、真正缺口、最多五个关键问题的答案 |
| 微规格与任务 | 7—10 分钟 | 10—14 分钟 | 测试接口、固定例子、1—3 个纵向任务 |
| 最小测试与实现 | 10—21 分钟 | 14—32 分钟 | 一条行为先失败，再最小实现通过；逐条扩展 |
| 双轴检查、处理问题 | 21—25 分钟 | 32—39 分钟 | 规格符合度、项目规范分别检查；只修影响验收的问题 |
| 演示、说明结果 | 25—30 分钟 | 39—45 分钟 | 可运行路径、真实输出、剩余边界和下一步 |

30 分钟优先完成第一个纵向任务；45 分钟再补异常、组合条件和分页。若到中点仍没有一条行为通过，立刻收窄范围。不要把最后五分钟继续花在生成代码上。

## 贯穿案例：先确认缺口，再写微规格

代码定位顺序是“页面发什么 → Controller 接什么 → Service 怎么查询 → Mapper 有无可复用能力”。本项目的证据如下：

| 位置 | 已有行为 | 对本题的意义 |
| --- | --- | --- |
| [SKU Controller](../../Cloth_management_System/src/main/java/com/xinrong/store/controller/SkuController.java) | `GET /api/skus` 接收分页、颜色和尺码 | 可以扩展现有接口，不必另建预警接口 |
| [SKU Service](../../Cloth_management_System/src/main/java/com/xinrong/store/service/impl/SkuServiceImpl.java) | 颜色模糊匹配、尺码精确匹配，按颜色和尺码排序 | 列表尚无库存查询条件；应在数据库分页前增加条件 |
| [SKU Mapper](../../Cloth_management_System/src/main/java/com/xinrong/store/mapper/SkuMapper.java) | 已有 `selectStockWarnings(threshold, limit)` | 这是工作台预警查询，不是现有 SKU 分页筛选 |
| [工作台 Service](../../Cloth_management_System/src/main/java/com/xinrong/store/service/impl/DashboardServiceImpl.java) | 预警调用固定阈值 2、条数 8 | 本题不重复开发工作台预警，也不修改其口径 |
| [SKU 页面](../../cloth-store-frontend/src/views/sku/index.vue) | 只有颜色、尺码筛选，库存小于 10 时高亮 | 高亮不等于可配置查询；页面需要新增筛选输入 |
| [SKU 请求封装](../../cloth-store-frontend/src/api/sku.js) | `getSkuList(params)` 已透传查询参数 | 通常可直接复用，无须新增一套请求方法 |

### 微规格：两分钟能讲完

**用户目标**：记货人员输入一个库存上限，直接看到库存不高于它的 SKU，仍可按颜色和尺码搜索。

**接口契约**：扩展已保护的 `GET /api/skus`，沿用 [Result](../../Cloth_management_System/src/main/java/com/xinrong/store/common/Result.java) 和分页结果结构。

| 参数或结果 | 约定 |
| --- | --- |
| `pageNum`、`pageSize`、`color`、`size` | 保留现有默认值与匹配方式 |
| `maxStock` | 可选非负整数，范围 0—2147483647；表示 `stock <= maxStock` |
| 未传或空值 | 不增加库存条件；前端清空时直接省略该参数 |
| `maxStock=0` | 只查库存为零的 SKU，不能用真假判断把 0 当成未传 |
| 多个条件 | 颜色、尺码、库存条件同时满足 |
| 成功 | 业务 `code=200`；`data.records` 与 `data.total` 都按筛选后的结果计算 |
| 非法阈值 | 负数、小数、非数字、超出整数范围均返回业务 `code=400` 和参数提示 |
| 页面 | 增加“库存不高于”整数输入；搜索或重置回第一页；重置清空所有筛选 |

示例请求：`GET /api/skus?pageNum=1&pageSize=10&color=demo-red-42&maxStock=2`。

参数错误复用 [全局异常处理](../../Cloth_management_System/src/main/java/com/xinrong/store/common/GlobalExceptionHandler.java) 的业务响应约定；不要擅自把“业务 code=400”写成“HTTP 状态必定为 400”。建议通过新的查询 DTO 绑定与校验，使绑定失败进入既有处理分支；不能只在页面限制输入，也不能假定普通 `Integer` 参数的所有转换错误都会自动得到想要的响应。

**范围外**：持久化阈值、工作台统计改造、库存写入、库存流水、推送通知、索引优化。本例保留 SKU 原有“小于 10 高亮”的展示含义，明确它与临时筛选条件不同；若面试官要求统一高亮，再作为明确新增范围处理。库存值采用实体 `Integer`，不由单次录入上限推断累计库存上限。

### 改动地图

正常改动范围是 [SkuController](../../Cloth_management_System/src/main/java/com/xinrong/store/controller/SkuController.java)、[SkuService 接口](../../Cloth_management_System/src/main/java/com/xinrong/store/service/SkuService.java)、[SkuServiceImpl](../../Cloth_management_System/src/main/java/com/xinrong/store/service/impl/SkuServiceImpl.java)、[SKU 页面](../../cloth-store-frontend/src/views/sku/index.vue)，以及新增查询 DTO、行为测试。现有 Mapper 的分页能力可复用，通常只需给查询条件增加 `le`，不改库存更新 SQL、不加表字段。

先查受影响调用点再改方法签名，复用项目的鉴权、返回结构和逻辑删除机制。将页面当前页的数组过滤成低库存列表会使总数和其他页不正确，不符合契约。

## 从 1—3 个纵向任务开始

每项都能独立演示用户结果，不拆成“先写所有后端、再写所有前端、最后补所有测试”。

1. **阈值为 2 时列表正确筛选**：输入 → 请求参数 → 数据库过滤与分页 → 页面显示 → API 行为测试。包含等于 2 的 SKU，排除库存 3 的 SKU。这是最小可交付任务，无任务前置依赖。
2. **零值与非法阈值有正确反馈**：在第一项之后补 0、负数、小数等例子，贯穿输入、后端校验、错误响应及页面提示。依赖第一项的查询入口。
3. **与颜色、尺码及分页组合使用**：在第一项之后补交集、总数、翻页、清空条件与回到第一页；不因编号而人为依赖第二项。

正式调用 `to-tickets` 时，先让面试官确认拆分，再按 [本地任务约定](../agents/issue-tracker.md) 一票一文件。时间很短时先在对话里写这张清单，借鉴纵向拆分的方法，不必为了流程创建整套文档。

## 六段可以直接用的提示词

这些提示词按六个技能的核心方法压缩，按现场需要选择。短题可以直接“澄清 → 一条测试 → 实现 → 演示”，不需要全部启动。正式使用原版技能时，先读相应原文；其中的用户确认、显式调用和依赖要求仍然有效。

要真正使用技能，应在工具的技能选择器中明确选择，或提供本节链接中的本地 `SKILL.md` 路径并要求读取执行，不能仅凭提示里出现名称就假设已加载。仓库技能位于 `.agents/skills/`；`grill-with-docs`、`to-spec`、`to-tickets` 保留了禁止隐式调用的元数据。采用渐进读取：先载入当前选中的原文，再按其引用读取必要依赖，不一口气把所有技能塞入上下文。使用依赖委托型技能时，应确认被委托的技能也可用。

### 1. grill-with-docs：让 AI 找事实，让人定口径

对应原文：[grill-with-docs](../../.agents/skills/grill-with-docs/SKILL.md)，依赖 [grilling](../../.agents/skills/grilling/SKILL.md) 和 [domain-modeling](../../.agents/skills/domain-modeling/SKILL.md)。

```text
借鉴 grill-with-docs 的澄清方法完成这道现场题。先读 AGENTS.md、GLOSSARY.md，以及 SKU 页面、请求封装、Controller、Service、Mapper，列出已有能力和真正缺口。
全程最多提出 5 个关键问题，工具和环境问题合并询问；事实由你查代码，不要让我代查。每个业务问题给出建议答案，按依赖顺序询问，等我确认再决定。
目标是 SKU 列表的临时库存上限筛选。先不要改业务代码；只有确实出现新领域术语或重要取舍时才建议补领域文档。
```

对面试官说：

> 我看到工作台已经有固定阈值的预警查询；这次缺的是 SKU 分页列表的临时筛选。我会保留现有能力，先把包含等号、零库存和组合条件这几个会影响实现的规则问清。

### 2. to-spec：把回答压成可核对的微规格

对应原文：[to-spec](../../.agents/skills/to-spec/SKILL.md)。原版用于合成已讨论的决策，完整模板包含用户故事等部分；短题借用其决策记录方式即可。

```text
借鉴 to-spec，把刚才已经确认的答案整理成一页以内的微规格，不增加新需求、不重新展开采访。
写清用户目标、maxStock 参数契约、Result 与分页结果、3 个固定输入/期望、范围外事项。先提出最高的可用测试接口及其能验证和不能验证的内容，等我确认。
默认建议通过受保护的 HTTP 接口和隔离 MySQL 验证真实筛选与分页；环境不可用时单独说明验证范围。产物留在本地，不发布远程 Issue。
```

对面试官说：

> 我先把口头约定变成几条可以逐项核对的验收条件。最关键的是不传参数保持原查询，传 0 仍生效，筛选发生在分页之前。

### 3. to-tickets：只拆 1—3 个能交付的行为

对应原文：[to-tickets](../../.agents/skills/to-tickets/SKILL.md)。

```text
借鉴 to-tickets，将确认的微规格拆成最多 3 个纵向任务。每项给出用户可见结果、验收例子和真实阻塞项，覆盖接口、查询、页面及相应验证。
第一项必须能在十分钟左右形成最小演示；不要按 Controller、Service、前端分成三张互相不能验收的任务。
先展示清单等我确认，不创建远程任务。若总时间只有 30 分钟，优先完成阈值 2 的正常路径，再按剩余时间补边界。
```

对面试官说：

> 我先打通一个用户行为：输入 2，返回并显示库存 0 和 2 的规格。之后每加一项边界都有可观察结果，避免最后才把前后端拼起来。

### 4. tdd：一次失败测试，只推进一个行为

对应原文：[tdd](../../.agents/skills/tdd/SKILL.md)、[测试示例](../../.agents/skills/tdd/tests.md)、[Mock 约定](../../.agents/skills/tdd/mocking.md)。

```text
测试接口和例子已确认。请按 tdd 一次只推进一条行为：先写“库存上限 2 返回 0、2，排除 3”的公共接口测试，运行并解释失败原因，再做最小实现并重跑同一测试。
使用独立固定期望，不复制查询公式生成断言，不用内部 Mapper 调用次数替代结果验证。先确认编译、鉴权和数据库基线正常；连接失败或编译失败不算这个业务行为的 Red。
第一条通过后再提出下一条边界测试；不批量生成所有测试与实现，不顺手重构无关模块。
```

对面试官说：

> 我要先看到一条能抓住本题缺口的失败，而不是只看到编译器报错。然后只加足以让这条行为通过的实现，这样我能解释每次修改解决了什么。

### 5. code-review：规格和规范分别看

对应原文：[code-review](../../.agents/skills/code-review/SKILL.md)。

```text
对本次任务的文件做双轴检查，只报告影响交付的具体问题。先列出比较基准和文件清单，包含新增 DTO、测试与未提交改动，避免空 diff 漏审。
Standards：按 AGENTS.md 和邻近代码检查职责、参数校验、命名、重复与越界改动；启发式坏味道注明是判断，不当成硬规则。
Spec：逐条检查 <=、零值、未传参数、组合条件、数据库分页、total、搜索重置及非法输入。两轴分别给出证据和结论，不相互抵消。
若使用原版 code-review，先确保存在从固定提交到 HEAD 的有效差异，再让两个独立子代理分别审查；未提交的现场代码则明确使用工作区审查方式，不假称三点 diff 已覆盖。
```

对面试官说：

> 我会分别检查“有没有做对题目”和“有没有遵循这个项目的写法”。这一题重点看 0 有没有丢失、总数是否真按筛选计算，以及有没有为了查询误改库存写入逻辑。

开始时记录基线提交和 `git status --short`。原版技能使用 `git diff <基准>...HEAD`，它不会包含工作区未提交变化。若面试官允许本地提交，先逐项确认文件清单，只提交本题自己的改动，再用已记录的基线运行原版审查；不要顺带提交原有改动。未获提交授权时，借鉴双轴方法查看实际工作区差异并单独读新增文件，明确这属于工作区审查，不称为完整运行原版技能，也不为了凑比较区间擅自提交。

### 6. diagnosing-bugs：卡住时让反馈变得更明确

对应原文：[diagnosing-bugs](../../.agents/skills/diagnosing-bugs/SKILL.md)。

```text
当前具体症状是：<填写实际症状>。请先用一条可重复运行的命令复现同一个问题，断言具体错误并展示脱敏输出；没有可失败的反馈命令，先解决复现条件，不直接猜代码。
最小化复现后，列出 3—5 个可证伪假设，每个给预测，按可能性排序；一次只改变一个变量验证，日志加唯一标记。
找到原因后，在正确公共接口处先保留回归测试，再最小修复；用最初的完整复现命令复验，清除临时探针。若缺少必要环境，说明卡在哪个前置条件，不伪造复现结果。
```

对面试官说：

> 我先把失败缩成一条能重跑的请求，区分是参数没传、查询条件没加，还是结果被页面错误处理。接下来每次只验证一个假设，避免反复让 AI 大面积重写。

## 测试例子与演示怎么落地

在隔离数据中准备四个 SKU，记下实际创建得到的 ID。颜色使用本轮唯一的短标识，避免混入其他数据。期望来自下表，不依赖生产代码计算。

| 标识 | 颜色 | 尺码 | 库存 |
| --- | --- | --- | --- |
| A | demo-red-42 | 110 | 0 |
| B | demo-red-42 | 120 | 2 |
| C | demo-red-42 | 130 | 3 |
| D | demo-blue-42 | 120 | 1 |

| 顺序 | 请求或操作 | 业务期望 |
| --- | --- | --- |
| 第一个 Red → Green | 颜色 demo-red-42，`maxStock=2` | 只含 A、B，`total=2`；当前缺少条件时会错误包含 C |
| 零值 | 同颜色，`maxStock=0` | 只含 A |
| 原查询兼容 | 同颜色，不传 `maxStock` | A、B、C，`total=3` |
| 组合条件 | 同颜色、尺码 120、`maxStock=2` | 只含 B，D 不得混入 |
| 分页 | 同颜色、`maxStock=2`、`pageSize=1` | 每页一条，第一页和第二页合起来为 A、B；两页 `total` 均为 2 |
| 非法输入 | `-1`、`1.5`、`abc`、`2147483648` | 各自得到业务 `code=400` 和参数提示 |
| 页面重置 | 翻页后改变条件，随后重置 | 搜索回第一页；重置后省略 `maxStock` 并恢复原查询 |

首先约定 HTTP API 为主要测试接口：真实运行 Controller、Service、Mapper 和隔离数据库，使用测试账号或约定的认证夹具。鉴权失败会遮住筛选行为，必须先排除。数据准备可以使用夹具，断言仍通过接口返回值完成；不要 Mock 自有 Mapper 后声称已验证真实 SQL 和分页。

下面是测试类建好后的命令模板，从后端目录执行；类名按现场实际命名调整：

```text
mvn -Dtest=SkuLowStockFilterTest test
```

每次保留命令、真实输出和对应行为的判断。先跑目标测试，结束前再按可用时间跑项目要求的检查；前端在其目录执行 `npm run build` 检查构建，并通过页面验证参数、结果和重置。构建成功不能替代接口断言。

准备好测试登录态后，可在 PowerShell 展示同一条真实请求。`DEMO_TOKEN` 使用现场测试账号得到的 Token，终端不要输出其值；地址按实际环境调整：

```powershell
$demoHeaders = @{ Authorization = "Bearer $env:DEMO_TOKEN" }
$demoBaseUri = 'http://localhost:8080'
$demoResult = Invoke-RestMethod -Uri "$demoBaseUri/api/skus?pageNum=1&pageSize=10&color=demo-red-42&maxStock=2" -Headers $demoHeaders
if ($demoResult.code -ne 200) { throw $demoResult.message }
$demoResult.data.records | Select-Object id, color, size, stock
$demoResult.data.total
```

最后按“输入 2 → 看到 A、B → 输入 0 → 只剩 A → 清空 → A、B、C → 非法输入得到反馈”演示。打开网络面板核对请求参数、响应 `records` 和 `total`，再说明具体改动与测试。若某一步失败，就展示实际失败及定位结论，不跳过去宣布完成。

## 条件不理想时怎么继续

| 情况 | 合理处理 | 对面试官的表达 |
| --- | --- | --- |
| 没有 Skills 或选择器 | 使用上面的普通提示词，人工完成澄清、切片、测试和审查；无需现场搭插件体系 | “这些工程方法可以直接落在提示词和验证上，我先按现有工具完成闭环。” |
| 无法联网 | 读本地源码和现有资源，复用已缓存依赖；缺依赖时先确认可用替代方案，不长时间折腾安装 | “我先使用环境已有能力；缺失的依赖会影响哪些验证，我会单独说明。” |
| 数据库缺失 | 先确认能否提供隔离 MySQL；否则协商把交付缩到页面交互或参数校验等可独立验证部分，单独说明真实查询尚待验证 | “这个筛选依赖数据库执行；我可以先演示可验证的部分，真实分页结果需要数据库确认。” |
| 本地基线不能编译 | 确定是否为题目要求解决的问题；若是环境或缺失源码，立即展示最短失败证据并与面试官确定起点 | “目前失败发生在功能之前，我先确认基线问题是否在考察范围，避免把两项任务混在一起。” |
| AI 卡住或连续生成错误 | 停止重复大提示词，收窄到一个函数、一条请求或一处报错；给源码片段、输入和期望，必要时自己写最小修改 | “这一轮输出没有推进验证，我缩小问题并亲自核对关键条件。” |
| 剩余时间不足 | 保住已通过的纵向行为，停止扩展；优先演示与说明未完成项 | “正常路径已达到这个验收点，剩余边界是这些；我先展示可运行结果，再说明下一步。” |

数据库不可用时，内存数据演示或 Mock 响应只能验证被替代后的那部分行为；选择它们应出于现场明确的交付取舍，不能用来证明 MySQL 查询、分页或逻辑删除已正确。

## 三轮练习：把方法练成自己的判断

练习时记录真实耗时；每轮结束先对照标准复盘，再进入下一轮。重点不是提示词背得多熟，而是自己能读懂代码、作出取舍，并解释验证结果。

| 轮次 | 怎么练 | 可交付物 | 自测标准 |
| --- | --- | --- | --- |
| 第一轮：读代码，手写微规格，30—45 分钟 | 前十分钟先自己沿 SKU 页面 → 请求封装 → Controller → Service → Mapper 阅读；再用 AI 核对遗漏。手动写出本例契约、固定数据、改动范围和范围外内容 | 一页微规格、请求链路笔记、四个 SKU 的期望表、1—3 项纵向任务 | 不看 AI 回答，能说明工作台预警与列表筛选的区别；解释为什么条件必须在分页前、为什么 0 不能当空值、哪些文件需要改、为什么通常不用新表 |
| 第二轮：带着 AI 实现，45—60 分钟 | 在自己的练习分支中按需选用上述提示词；先确认测试接口，再逐条 Red → Green；每次先看 diff，再接受下一轮改动；最后双轴审查与演示 | 可运行的局部改动、目标行为测试、真实失败及通过输出、页面演示、审查结论 | 第一条失败确实来自阈值缺失；正常、零值、缺省、组合、分页与非法输入逐项核对；能解释新增查询条件及错误如何到达页面，不能只会运行命令 |
| 第三轮：限时模拟，30 或 45 分钟 | 请同学扮演面试官；前五分钟只给模糊需求，中途加入一项变化或故障。自己决定问题优先级、工具选择和止损时间 | 计时记录、最终微规格与真实完成范围、最短复现及定位笔记、两分钟交付讲述 | 问题控制在五个以内；临时变化能同步影响契约与测试；遇到失败先缩小反馈循环；最后五分钟能展示实际结果并清楚交代剩余项 |

第三轮可以轮换两类挑战，不要一次叠加所有干扰：

- **临时变化**：“低库存改为严格小于阈值。”先确认等号规则已变，再修改期望：阈值 2 只包含库存 0，不再包含库存 2。说明这会改变哪条测试和查询条件，而不是直接要求 AI 全量重写。
- **失败定位**：在练习副本中故意漏传零值参数，或让翻页后搜索不重置页码。先观察请求与响应，再提出能区分前端参数、后端条件和分页状态的假设。若模拟数据库不可用，先识别环境前置条件，避免围绕筛选 SQL 反复猜测。

每轮用五项各记 0 或 1 分：**能独立解释链路、能收敛需求、能选择合适工具、能设计抓得住缺口的测试、能展示与解释真实结果**。低于 4 分就重练失分环节；达到 4 分后更换一个同等大小的需求，检查自己迁移的是方法，而非只记住 `maxStock` 的答案。

收尾可以说：

> 这个功能把需求约定落实到了同一条用户路径：参数进入、数据库筛选、分页返回、页面展示。这里是实际通过的检查和演示结果；这里是尚未验证或未完成的部分。后续我会优先补上这些边界，而不是继续扩展功能范围。
