# AI Coding 实践：30 个面试追问与口述练习

围绕简历中的规范驱动、AI 协作、质量排障、协作约束四条主线准备。每题先讲判断与具体例子，再接受递进追问；不要把技能名当成答案。

技能依据固定提交 `49dd158d1076134a641b33efb035946536778336`；业务依据现有源码及 [库存源码复盘](stock-review.md)。文中的验证方案使用“会怎样做”表述，实际运行结论以对应命令和结果为准。源码文件的公开跟踪与本地补充状态见源码复盘。

## 一、基础机制：先解释清楚自己在用什么

### 01｜这个项目里的 AI Coding，解决了什么问题？

**面试官想查什么：** 能否从真实业务出发说明 AI 的用途，而不是把使用工具本身当成果。

**30 秒回答要点：** 项目服务家里童装店的进销存登记。我把颜色尺码对应 SKU、进货加库存、销售扣库存、更正记录反向调整这些规则交给 Codex 辅助实现和联调。关键是把口述需求转成可验收行为，例如销售从 5 件改成 3 件，库存只回补 2 件；我需要检查业务记录、库存和流水是否对应。

**递进追问：** “那它和普通 CRUD 有什么区别？”

**核心回答：** 一条销售记录的修改会同时影响库存、流水和金额；失败还要整体回滚。难点是关联影响和边界，不能只证明某张表保存成功。

### 02｜Skill 和一段普通提示词有什么区别？

**面试官想查什么：** 是否理解可复用工作流，而不是把 Markdown 包装成新技术。

**30 秒回答要点：** 普通提示词描述眼前任务；Skill 把反复有用的步骤、检查条件、参考资料和工具用法放进有名称与触发说明的目录。比如排障技能要求先建立能捕获具体症状的失败信号，再最小化、验证假设和回归。它主要改变智能体的做事方法，不是训练模型，也不是业务运行依赖。

**递进追问：** “把所有提示词都放进去，不就更强了吗？”

**核心回答：** 不相关指令会消耗上下文并产生冲突。应只保留能改变实际决策的指导，细节按需读取，简单任务不必强行运行整套流程。

### 03｜Skills、AGENTS.md 和 MCP 分别负责什么？

**面试官想查什么：** 能否区分流程、项目约定和外部能力连接。

**30 秒回答要点：** AGENTS.md 说明这个仓库的稳定规则，例如库存走 StockService、沿用 Result、不要夹带无关文件。Skill 说明某类任务怎样做，例如怎样拆工单或审查。MCP 用于向智能体提供工具、数据等能力，例如访问 GitHub。三者可以配合：规则限定范围，技能组织流程，工具完成动作。

**递进追问：** “Skill 写了创建 Issue，就代表可以直接创建吗？”

**核心回答：** 不代表。执行还受当前任务授权、工具权限和项目跟踪配置约束。本仓库配置的是本地 Markdown 任务，技能里的 publish 应映射到该配置。

### 04｜什么叫渐进加载？为什么不是把全部 Skill 都塞进上下文？

**面试官想查什么：** 是否理解技能发现、内容读取和上下文成本。

**30 秒回答要点：** 先用技能的名称和 description 判断是否匹配；选中后读取 SKILL.md；再按任务读取相关参考或使用脚本。以 tdd 为例，入口定义行为测试和循环，tests.md、mocking.md 提供进一步例子。这样能减少无关内容，保留当前任务的重要信息，而不是每轮加载所有技能全文。

**递进追问：** “有名称就一定会自动执行吗？”

**核心回答：** 不一定，受客户端发现方式和调用策略影响。固定版本的 grill-with-docs、to-spec、to-tickets 保留显式调用设置，不能假定所有技能都会自动触发。

### 05｜为什么选这六个 Skills？它们如何对应简历四条主线？

**面试官想查什么：** 选择是否服务项目问题，能否形成完整解释。

**30 秒回答要点：** grill-with-docs、to-spec、to-tickets 对应需求澄清、规格和任务拆分，支撑规范驱动；tdd 用行为测试约束实现，code-review 独立审查变更；diagnosing-bugs 对应有证据的排障。协作约束由 AGENTS.md 及项目配置承接。它们覆盖从“要什么”到“怎么证明做对”的关键环节。

**递进追问：** “每次修改都从第一个 Skill 开始吗？”

**核心回答：** 按不确定性选择入口。需求已明确可直接规划或实现；出现稳定缺陷可先诊断；已有明确变更则直接审查。不为了凑流程重复已有决定。

## 二、Skills 逐项：解释机制，也能落到库存案例

### 06｜grill-with-docs 自己做了什么？为什么还有依赖？

**面试官想查什么：** 是否读过实际入口，能否解释追问与文档如何配合。

**30 秒回答要点：** 固定版入口很短，委托 grilling 和 domain-modeling。前者把决策排成依赖树，每轮讨论前置条件已明确的问题；事实由智能体查代码，业务选择由人决定。后者澄清商品、SKU、销售等术语，及时维护词表；确有重要取舍时再写 ADR。因此入口、依赖和项目上下文需要一起理解。

**递进追问：** “销售删除和退款这个词混用了，怎么办？”

**核心回答：** 先指出语义差异：当前删除销售是撤回登记并回补库存，付款状态为人工记录，没有支付退款。确定术语后更新词表与受影响规格；不是每次字段调整都需要 ADR。

### 07｜to-spec 和需求访谈有什么区别？什么是测试边界？

**面试官想查什么：** 规格能否指导实现与验收，是否把文件目录当需求。

**30 秒回答要点：** to-spec 根据已有讨论和代码综合规格，不另起需求访谈；但需要确认测试边界。边界是调用者能使用、能观察结果的公开接口，优先复用已有、较高层且足以覆盖行为的接口。销售更正可以通过销售修改接口执行，再用销售详情、SKU 和流水查询检查结果。规格还要写正常、失败及范围外内容。

**递进追问：** “为什么不把所有类名和方法写进规格？”

**核心回答：** 文件和内部结构容易变化，规格应保存业务与接口决策。比如“库存不足整体失败”比“在某文件第几行加判断”更稳定；实现路径放在定位材料中。

### 08｜to-tickets 的纵向切片和阻塞关系是什么？

**面试官想查什么：** 是否能拆出可独立验证的任务，避免最后才联调。

**30 秒回答要点：** 一张工单交付一条窄而完整的行为，跨越涉及的页面、接口、持久化和验证。例如“销售改少正确退库”同时包含编辑、保存、库存变化和流水查询。Blocked by 表示没有前项就无法开始的真实依赖，不是排期顺序。每项要能独立演示，规模适合一个新的上下文完成。

**递进追问：** “所有重构也都能这样切吗？”

**核心回答：** 广泛机械变更是例外，可采用 expand–contract：先兼容新旧形式，再分批迁移，最后删除旧形式。依赖边反映兼容关系和集成条件，不能强行拆成彼此无法保持可用的碎片。

### 09｜这个固定版 tdd 的循环是什么？重构在哪里做？

**面试官想查什么：** 是否知道所用版本的明确约定，而不是背通用口号。

**30 秒回答要点：** 该版本明确采用 Red → Green：先在约定公开边界写一条行为测试，看到它因目标行为失败，再写最小实现使其通过；一次推进一条切片。重构放在后续 review 阶段。这是该技能的具体流程安排，不代表对所有 TDD 实践重新定义。

**递进追问：** “给现有销售修改功能补测试，马上通过，算 Red 吗？”

**核心回答：** 不算，那是补充回归覆盖。真正的失败先行需要对应新规则或缺陷的失败信号；不能把环境起不来、断言写错或没有执行，冒充业务 Red。

### 10｜code-review 的双轴审查是什么？为什么先固定比较点？

**面试官想查什么：** 能否明确审查对象，并区分写法正确与需求正确。

**30 秒回答要点：** Standards 查仓库规范和需判断的代码异味；Spec 查要求是否实现、是否漏边界或扩大范围。固定版让两个子审查者并行检查并分别呈现结果，避免相互掩盖。开始前确认基准可解析、差异非空，用三点比较查看共同祖先到 HEAD 的变更，明确审查范围。

**递进追问：** “没有规格，Spec 方向怎么办？”

**核心回答：** 先找提交引用、用户指定位置及匹配文档；仍没有就询问来源。确认不存在时明确跳过该轴，不能由实现倒推需求后再给自己打通过。未提交修改也要单独约定比较范围。

### 11｜diagnosing-bugs 为什么坚持先获得失败信号，再列 3～5 个假设？

**面试官想查什么：** 是否会验证根因，而不是凭直觉修一处看似可疑的代码。

**30 秒回答要点：** 先建立一条可重复执行、能断言用户具体症状的命令，看到失败后逐步最小化。然后列出 3～5 个有排序、可证伪的假设，每个假设对应一条预测。探针一次改变一个变量，修复后既跑最小案例，也跑原始场景并清理临时日志。

**递进追问：** “如果复现不了，还能继续猜吗？”

**核心回答：** 按该流程应说明尝试过什么、缺什么复现环境或脱敏材料，先补反馈循环。偶发缺陷先提高可观测的复现率；性能问题先建立计时或分析基线，不能凭感受认定更快。

### 12｜这些流程怎样衔接，怎样避免文档和上下文越来越重？

**面试官想查什么：** 是否能把工具链用成轻量工程方法，而不是制造流程负担。

**30 秒回答要点：** 词表统一术语，规格固定行为，工单承接一条可验收切片，测试和审查围绕同一要求，排障记录保留根因与结果。AGENTS.md 只放稳定规则，单次任务细节放规格和工单；新上下文读取相关产物与代码即可，不复制整段聊天和无关历史。

**递进追问：** “规格变了，下面的工单和测试怎么办？”

**核心回答：** 找出受影响验收、阻塞关系和测试预期一起更新。不要仅改文字后仍用旧预期验证，也不要把所有原本可并行的任务排成线性队列。

## 三、真实源码：能从规则一路解释到数据变化

### 13｜为什么商品与 SKU 要分开？库存为什么要收口？

**面试官想查什么：** 是否理解领域对象，以及公共库存入口的价值。

**30 秒回答要点：** 商品描述一款衣服，SKU 表示它的具体颜色尺码组合，库存和价格在 SKU 上。进货、销售和盘点都会改库存，如果各自直接更新，容易遗漏流水或校验。统一 StockService 负责锁定规格、变更数量和写流水，业务 Service 负责何时加减及关联哪笔记录。

**递进追问：** “用公共 Service 就自动没有重复代码和错误了吗？”

**核心回答：** 它减少了分散写库存的入口，但调用方仍要给对数量、方向和业务关联，也要处理同记录并发。封装建立边界，不能替代对整条行为的审查与验证。

### 14｜业务记录、库存和流水为什么能在一个事务里？

**面试官想查什么：** 是否理解 Spring 调用链与原子性，能否解释失败路径。

**30 秒回答要点：** 进货和销售的新增、修改、删除方法有事务注解，调用另一个 Spring Bean 的 StockService；在默认传播和同一数据源下，库存更新、流水写入加入外层事务。新增销售先保存记录，若库存不足抛异常，目标是前面的销售记录也回滚。运行效果要通过失败场景查询三类结果核对。

**递进追问：** “同一个类里自己调用带事务注解的方法，也一定有效吗？”

**核心回答：** Spring 常见代理模式下，自调用不会经过代理，不能依赖内部方法注解新建事务。这里要沿真实 Bean 调用核对，不能看到注解就断言所有路径正确；异常也不能被吞掉后继续提交。

### 15｜已经有 FOR UPDATE，为什么还要 stock >= quantity？

**面试官想查什么：** 是否区分锁的互斥作用与更新语句的业务约束。

**30 秒回答要点：** StockService 先锁定 SKU，读取 beforeStock，再更新并写 afterStock 流水；这样有助于并发变更的前后值连续。扣减 SQL 使用 stock = stock - quantity，并带 stock >= quantity，数据库写入点再次保证库存足够。影响行数为 0 时按库存不足处理，异常交给外层事务。

**递进追问：** “只保留条件更新行不行？”

**核心回答：** 对单行防负库存，原子条件更新可以成立；但要可靠记录变更前后值，还要设计读写和流水的顺序。不能先普通查询旧值，再假定条件更新后流水前值仍准确；行锁也必须在事务内使用。

### 16｜销售数量修改和换 SKU，库存分别怎么变？

**面试官想查什么：** 能否用具体数值解释差量与补偿方向。

**30 秒回答要点：** 同一 SKU 只处理差值：销售从 5 件改 3 件回补 2 件，改 8 件再扣 3 件。换 SKU 不能只算一个差值，要回补旧 SKU 的原数量，再从新 SKU 扣新数量；新规格库存不够，应整体失败。进货方向相反，删除进货则从当前总库存扣回原数量。

**递进追问：** “进货已经部分卖出，还能判断哪一批被卖掉了吗？”

**核心回答：** 不能。当前检查的是 SKU 总库存是否足够扣回，系统没有采购批次追踪。不能把库存数量校验说成批次库存或先进先出成本核算。

### 17｜SKU 有行锁，为什么同一条销售并发修改仍有风险？

**面试官想查什么：** 能否识别正确库存算术之外的业务并发问题。

**30 秒回答要点：** 当前修改先普通 getById 读旧销售记录，再根据差值改库存。两请求都读到销售数量 5，分别想改 3 和 4，可能先后回补 2 和 1，但最终记录只有一次写入的数量；SKU 锁只把回补串行化，没有修正过期的业务基准。需要在业务记录层控制并发。

**递进追问：** “你会怎样改？”

**核心回答：** 可评估事务内锁定业务记录后再计算，或引入版本号并检查条件更新结果；失败要使本次库存变化一起回滚。再用同时修改、修改与删除等交错验证。跨 SKU 还要统一加锁顺序，避免反向交换形成死锁。

### 18｜防超卖和幂等是一回事吗？重复点击怎么处理？

**面试官想查什么：** 是否区分库存约束与一次业务意图只生效一次。

**30 秒回答要点：** 不是。库存 10 时，同一销售 2 件请求重复两次，两次都不超卖，却多记了一笔并多扣 2 件。当前未发现请求幂等键。前端禁用保存按钮能减少误点，后端还应按业务定义识别同一次提交或重试，不能只靠 UI。

**递进追问：** “怎么设计幂等键，怎样避免正常买两次被误判？”

**核心回答：** 以一次用户提交生成请求标识，限定使用范围，在事务内通过唯一约束防止重复处理，并记录可复用的结果；同键不同请求体要拒绝。两次独立购买使用不同标识，不能仅按商品、数量相同去重。

### 19｜用了 BigDecimal，金额就一定没问题了吗？

**面试官想查什么：** 是否考虑计算精度、舍入顺序和存储容量。

**30 秒回答要点：** BigDecimal 避免二进制浮点误差，代码先把单价 HALF_UP 到两位，再乘整数数量，后端重新算总额。但 DTO 允许数量和单价分别达到 999999，total_amount 却是 DECIMAL(10,2)，最大 99,999,999.99；合法输入组合仍可能溢出。还要明确单价小数位、总额上限与异常提示。

**递进追问：** “直接把数据库字段改大就完了吗？”

**核心回答：** 要先定业务容量和舍入口径，再统一 DTO、总额校验、数据库精度及展示。改大列解决容量的一部分，不能代替上限、负数、过多小数和边界组合的验证。

### 20｜JWT 和管理员权限在前后端怎么衔接？

**面试官想查什么：** 是否区分身份认证、授权与界面隐藏。

**30 秒回答要点：** 登录用 BCrypt 校验密码并签发 HS256 JWT；后端拦截器校验签名、过期时间，再查用户存在和启用状态，对 /api/user 及子路径判断 ADMIN。前端附加 Bearer Token，统一处理 401、403，并用路由控制管理员页面。真正权限判断在服务端，隐藏菜单只是交互层。

**递进追问：** “禁用用户和修改密码，旧 Token 都会立刻失效吗？”

**核心回答：** 禁用会被每次请求的用户状态检查阻断；当前未发现密码修改后的主动撤销机制。该设计也只有简化角色判断，没有细粒度权限表、租户隔离或完整 Token 刷新体系。

### 21｜图片上传和库存流水有哪些容易被问穿的边界？

**面试官想查什么：** 是否能准确解释外部服务和追溯能力。

**30 秒回答要点：** 上传组件单独携带 Token，服务端检查空文件、5MB 大小及扩展名，用日期目录与 UUID 生成对象名并上传 OSS。库存流水保存数量前后值、变化量、类型和业务关联。两项都是具体能力：扩展名校验不等于验证图片内容，数量流水不等于完整审计平台。

**递进追问：** “为什么不能称完整审计？”

**核心回答：** StockRecord 没有操作者字段，查询中的商品名、颜色尺码来自当前关联表而非历史快照，也没有防篡改设计。OSS 同样未见签名 URL、旧图片清理或图片魔数验证，描述要对应代码。

## 四、验证与排障：说明证据如何产生

### 22｜怎样验证销售改少退库，测试的预期从哪里来？

**面试官想查什么：** 测试是否观察业务行为，断言是否独立于实现。

**30 秒回答要点：** 用隔离数据：初始库存 10，新增销售 5 后应是 5，把该销售改 3 后应是 7。经约定的销售接口执行，再查销售数量、SKU 库存和关联流水，核对 +2 变化。预期 7 来自手算业务例子，不复制生产代码的差值公式；同时设计库存不足时三类数据保持原状的失败场景。

**递进追问：** “为什么不只断言 increaseStock 被调用一次？”

**核心回答：** 方法调用正确不代表参数、事务和持久化结果正确，而且会绑定内部结构。应在约定公开接口观察行为，避免把内部调用次数当作库存正确的证明。

### 23｜进货商切换后还能提交旧商品，怎样排查？

**面试官想查什么：** 能否把 UI 状态与后端校验分层诊断。

**30 秒回答要点：** 先固定 A、B 进货商及各自商品和 SKU，构造“选 A 商品后切 B，仍带 A 的 productId”这个症状的失败断言，再缩到最少操作。假设可包括列表没过滤、切换没清旧值、后端只查 ID 存在；分别用选项、请求体和直接 HTTP 请求区分。当前代码有筛选、清空和归属校验，可据此设计回归。

**递进追问：** “修好前端联动够了吗？”

**核心回答：** 不够，旧表单或直接请求仍可能绕过页面。要验证错误组合被后端拒绝，且没有新增进货、库存和流水；正常组合仍应成功。完整循环还要返回原页面路径复测。

### 24｜为什么库存测试不能全用 Mock？所有依赖都必须真实吗？

**面试官想查什么：** 是否知道隔离测试与真实数据库语义各自证明什么。

**30 秒回答要点：** 库存关键路径按约定的公开接口与隔离 MySQL 验证，覆盖真实行锁、SQL 条件扣减和事务回滚。该技能要求避免 Mock 自有 Mapper、Service 等内部协作者，以外部可观察行为作断言。外部 OSS、时间或随机数可以在系统边界替换，避免真实费用和不确定性。

**递进追问：** “能直接查表断言吗？”

**核心回答：** 对这里选定的 HTTP 行为边界，应优先用既有查询接口观察，避免旁路内部表制造耦合。若要验证数据库适配器本身，需另行明确边界和目的，不能混同两种测试结论。

### 25｜库存输入异常，怎样判断错在前端、DTO 还是数据库？

**面试官想查什么：** 是否理解输入转换、校验和异常传播的顺序。

**30 秒回答要点：** 固定合法请求，一次只替换一个值：负数、超业务上限、超大整数、小数、非数字，记录在哪一层拒绝。JSON 转换可能先于 @Valid 失败，业务范围由 DTO 检查，关联与库存由 Service 检查，数据库还有列容量。全局异常处理和 Axios 要把相应 message 传到用户，而不是都显示笼统失败。

**递进追问：** “Long 加 @Max，是否已经严格限制只能整数？”

**核心回答：** 不能这样推导；当前未见显式禁止浮点转整数的配置，SKU 前端也未单独断言整数。要直接验证类型转换行为。另外单次输入上限不等于多次进货后的累计库存上限。

### 26｜构建、contextLoads、业务回归和并发测试分别说明什么？

**面试官想查什么：** 是否把验证结果扩大解释，能否设计适合风险的证据。

**30 秒回答要点：** 前端构建说明能打包；contextLoads 检查 Spring 上下文加载，当前后端只有这一项测试。业务回归需验证给定操作的记录、库存和流水结果；并发测试还要控制请求交错并检查最终不变量。报告应包含版本、环境、数据、命令、预期和实际输出，让别人能复核。

**递进追问：** “并发跑一百次都过，就证明永远没问题吗？”

**核心回答：** 不能。要结合锁和事务的设计分析，构造同记录修改、重复删除、反向换 SKU 等针对性交错。通过的场景提供有限证据，不是覆盖所有调度，也不能无基线声称吞吐提升。

## 五、个人贡献与取舍：把人负责的决策讲具体

### 27｜AI 输出代码后，你具体检查什么？

**面试官想查什么：** 能否主动判断代码，而不是接受一份看起来完整的回答。

**30 秒回答要点：** 我按需求、接口、数据影响和差异四层检查。以销售更正为例，先核对改少、改多、换 SKU 的方向，再看是否复用 StockService、事务能否覆盖业务与流水、金额是否后端计算、错误提示能否到页面。最后核对改动文件与实际验证结果；构建通过后仍需检查业务场景。

**递进追问：** “AI 说已经防并发，你如何判断？”

**核心回答：** 要求它指出锁的对象、持有范围和受保护的不变量，再反例推演同记录并发。SKU 锁不能保护读取旧销售数量的过程；这样的反例比接受一句‘加了锁’更有价值。

### 28｜AI 写了代码，你的贡献怎样说明？

**面试官想查什么：** 是否有业务理解、技术判断和独立解释能力。

**30 秒回答要点：** 我用需求判断、场景取舍、问题反馈和验收解释贡献，而不是给 AI 生成行数编比例。能够拿“销售改少退库”讲清输入、期望、代码链路、异常和验证设计，也能指出当前并发与金额容量缺口。具体完成过的事情用提交、需求记录和运行结果证明。

**递进追问：** “让你现场不用 AI，能做什么？”

**核心回答：** 先独立画出商品、SKU、销售与库存关系，手算正常及失败案例，再定位 Controller、Service、Mapper 和事务边界；能解释一条 SQL 和构造一个反例。陌生实现细节查证后再答，不编造熟练程度。

### 29｜怎么约束智能体别乱改文件、泄露凭证或乱推送？

**面试官想查什么：** 是否理解协作范围、权限和可审查交付。

**30 秒回答要点：** 任务中给明确文件范围和验收，AGENTS.md 固定公共约定；提交前逐项检查差异和暂存清单，避免把未审查的本地文件一并加入。日志与请求材料去掉 Token、密码和云密钥，外部写入按当前授权执行。规则文件帮助协作，真正执行还依赖工具权限和人工审阅。

**递进追问：** “开源 Skill 可以直接复制，后续随 main 更新吗？”

**核心回答：** 要保留来源、固定版本与许可，并检查依赖和引用文件。更新要审查行为差异及原有配置，不能只看名称相同。仓库有 upstream-lock.json 和离线校验脚本，可核对引入文件完整性；这类检查不验证业务。

### 30｜下一步怎样改进，为什么先做这些？

**面试官想查什么：** 是否会按风险与成本排序，避免把所有改进都叫高并发优化。

**30 秒回答要点：** 先核对公开源码与本地依赖，形成可复现构建，再用隔离数据补库存、关联校验和权限回归。随后分开处理同记录并发、重复提交、稳定锁序及金额容量：每项先定语义和预期，再实现验证。没有容量证据前，先处理已能指出的数据正确性风险，避免过早引入复杂中间件。

**递进追问：** “用户只要求学 Skills，你会顺手把这些风险全部修了吗？”

**核心回答：** 不会扩大任务范围。先把发现、影响和可验证方案交付，按明确需求选择要实施的项；修复时保持小范围、可审查并补对应验证。工程判断也包括决定本轮不做什么。

## 10 分钟口述演练

每分钟用约 40 秒讲主线，剩余时间回答递进问题。练习时关掉答案，只保留题目；卡住的地方记下来，回到代码或技能原文核实。

| 时间 | 主线 | 自测追问 |
| --- | --- | --- |
| 00:00～01:00 | 用销售从 5 改 3 介绍项目、AI 分工与业务难点 | 为什么不是只做 CRUD？ |
| 01:00～02:00 | 解释 Skill、AGENTS、MCP 和渐进加载 | 为什么不加载所有技能？ |
| 02:00～03:00 | 用 grill 明确术语，用 to-spec 固定行为和测试边界 | 销售删除和退款有什么区别？ |

| 05:00～06:00 | 固定比较点，分别给出 Standards 与 Spec 检查项 | 没有规格时如何处理该轴？ |
