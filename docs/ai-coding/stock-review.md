外层进货/销售方法带事务，调用另一个 Bean 的库存方法，默认共同参与单库事务。库存先锁定 SKU，读取前值，再执行增减与流水写入。行锁帮助流水前后值连续，条件扣减约束库存不变负；运行回滚效果仍需实际验证。

同 SKU 修改只处理数量差：销售 5 改 3 回补 2；进货 5 改 3 扣回 2。换 SKU 需要分别撤回旧数量和应用新数量，不能只在新 SKU 上计算差值。

## 适合后续 Skills 练习的问题

| 问题 | 代码证据与影响 | 后续可验证方向 |
| --- | --- | --- |
| 同记录并发修改/删除 | 普通读取旧业务记录，缺少记录锁/版本号；SKU 行锁不能阻止重复计算差额 | 两请求同时更正或删除同一销售，验证最终记录、库存与流水 |
| 重复提交 | 未发现请求幂等键或唯一业务请求号 | 固定同一业务请求重试，先明确应记一笔还是两笔 |
| 跨 SKU 锁顺序 | 按旧规格再新规格加锁，反向交换可能产生死锁 | 定义稳定锁序并用相反方向并发场景验证，不能假定已有重试 |
| 金额容量 | DTO 允许数量和单价均 999999，但总额列为 DECIMAL(10,2) | 定义总额上限、两位小数和错误提示，验证数据库容量边界 |
| 数值类型与累计上限 | Long 范围注解不等于严格拒绝小数，单次上限不等于累计上限 | 直接请求验证小数、超大整数和多次累加 |
| SKU 重复 | 应用 count 后 insert，未发现规格组合唯一索引 | 并发新增同颜色尺码，讨论约束和历史重复数据 |
| 流水边界 | 无操作者和历史元数据快照 | 明确只是库存数量追溯，是否需要进一步审计另作规格 |

针对这些风险，先明确业务规则，再设计能区分正确与错误行为的复现场景；完成后将结果附到对应任务。

## 回归验收设计

以下场景通过既有销售/进货接口、SKU 查询和流水查询观察行为。测试接口需在真正执行前约定，使用隔离数据；不能把直接查询内部表代替全部对外验收。

| 初始状态与操作 | 独立业务期望 |
| --- | --- |
| 库存 10，新增销售 5 | 库存 5，新增一条销售及数量 -5 的关联流水 |
| 上例把销售 5 改 3 | 库存 7，销售数量 3，新增 +2 流水 |
| 库存不足，尝试扩大销售数量 | 操作失败，原销售、库存和流水保持不变 |
| 换成库存不足的另一 SKU | 整体失败，原 SKU 不得留下单独的回补 |
| 删除进货而总库存不足扣回 | 失败，进货和库存保持不变 |
| 错误进货商与商品组合直接请求 | 失败，无进货、库存和流水副作用 |

每项保存环境、版本、初始数据、请求、预期、实际输出及清理记录。当前实现已经通过的补测属于回归覆盖；真正的 TDD 需针对新规则或缺陷观察失败，再做最小实现。

## 其他面试边界

管理员控制是简化的 ADMIN/STORE_OWNER 角色判断，没有细粒度权限表或租户隔离。每次保护接口查用户状态，禁用可影响旧 Token，但未发现密码修改后主动撤销 Token。

销售额和收款额来自人工登记，不能说接入支付、利润核算或财务对账。图片上传有大小、扩展名检查，不能描述为完整内容安全、签名 URL 或旧对象清理方案。项目没有已核对的容器部署配置和生产容量证据。
