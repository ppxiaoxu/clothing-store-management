# 销售更正与库存联动：学习规格草案

Status: draft

此文档根据现有本地行为整理，供 `to-spec` 学习；不是历史需求产物、已批准的开发任务或测试报告。测试接口为建议，真正实施前需结合用户目标确认。

## Problem Statement

门店录错销售数量或规格后，需要修正记录，并使库存、流水和金额反映同一笔更正，避免只改表单而账实不符。

## Solution

允许更正销售记录；同规格按新旧数量之差调整库存，更换规格时分别撤回旧销售和应用新销售。库存不足则整体失败，保留原状态并显示具体原因。

## User Stories

1. 作为记货人员，我想把销售 5 件改成 3 件，以便退回多扣的 2 件库存。
2. 作为记货人员，我想增加销售数量，以便补记漏记部分；库存不够时收到拒绝提示。
3. 作为记货人员，我想改正颜色或尺码，以便两个规格分别恢复正确库存。
4. 作为记货人员，我想看到对应流水，以便理解更正带来的数量变化。
5. 作为记货人员，我想看到后端重算的金额，以便数量、单价与统计一致。

## Implementation Decisions

- 使用已有销售更正与查询接口、库存查询和流水查询，不为测试新造业务入口。
- 同规格只变更差量；更换规格按旧数量和新数量分别处理。
- 销售记录、库存和流水共同提交或共同回滚。
- 单价按现有规则保留两位小数，总额由后端计算；金额容量风险单独澄清，不能以此草案宣称已解决。
- 本例以合法且明确的整数数量为输入，严格小数拒绝和累计上限另行定义。

## Testing Decisions

- 建议以 HTTP API 与隔离 MySQL 为最高公共边界，用查询接口观察库存、销售和流水。
- 独立预期：初始 10，销售 5 后为 5，改成 3 后为 7；不能复制实现公式生成断言。
- 覆盖改少、改多、数量不变、换规格成功、换规格库存不足整体回滚。
- 页面层验收编辑保存、错误提示与刷新结果；不以 Mock 或构建成功证明数据库行锁。
- 现有只有上下文启动测试；本例暂未执行。已有行为直接通过的新增断言记为回归覆盖。

## Out of Scope

真实退款、独立退货单、批次成本与利润、多门店隔离，以及尚未实现的幂等、记录并发控制和稳定锁序。
